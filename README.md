# dsh-daily

每天 11:00，把 DSH 插件生态筛一遍，产出两样东西：**在别人已发布的作品上往前走一步**的具体改法，以及**生态里还没有的新方向**；你点一下，agent 就独立实现一个版本，发到**你自己的**仓库。

A daily brief for DeepSeek Harness. It reads the published plugin ecosystem against your own profile, proposes concrete deltas on other people's work plus directions nobody has built yet — and turns one click into an independently implemented repository, never a fork.

## 它解决什么

插件生态里已经有几千个包，靠人翻是翻不完的。但"每天推荐 N 个"本身没什么价值——真正贵的是**看完之后动手**。所以这个插件把两件事分成不同节拍：

| | 频率 | 成本 | 谁做 |
| --- | --- | --- | --- |
| **日报**：改进项 + 灵感 + 证据 | 每天 11:00 自动 | 一次模型调用 | 插件 |
| **开发 + 发布** | 你点「做这个」才发生 | 一整个开发流程 | agent |

**它不会每天自动造一个仓库。** 那样一个月就是 30 个仓，绝大多数是噪声。批准的权力在你手上，插件只负责把选项摆好、把活递出去。

日报产出两栏，来源不同、规矩也不同：

**改进项** —— 拿别人已经发布的插件当靶子。核心字段是 `delta`：**原版是 A，我要做成 B**。只写「做得更好」「增强体验」这类空话的会被直接丢弃——因为那种话读起来像答案，实际什么都没说。

**灵感** —— 生态里还没有、你自己可以立的新方向。没有来源仓库可锚定，所以规矩只有两条：字段不能缺，证据要么引用真实存在的东西、要么老实写「无直接证据」。界面上后者会打「未经证实」的标记——**它就是推测，不该长得像调研结论**。

两栏都会防重复：改进项按**来源仓库**记（同一来源不再出现），灵感按**标题**记并回灌进 prompt（同一方向不再重复提）。

## 为什么日报不全是开发工具

这是踩过的一次坑。插件读的画像（agent 记忆 + 工作约定）通篇是工程纪律：证据边界、安全门、密钥扫描、开源同步。模型照实读，于是交回来的 8 条全是网关、台账和门禁——**这是正确行为，是画像把它塑造窄了。**

候选池从来不是问题：它按 23 个生态分类轮转取样，`Just for Fun`、`Themes & Appearance`、`Voice & Audio` 本来就在里面（实测 60 条覆盖 23/23 个分类）。所以修的是两处指令：

- **画像**多一节「非官方来源的插件」。官方 bundle 是 harness 本身，其余的（含 `dsh-holdem`）是他自己写或特意装的——把兴趣范围摆到模型眼前，而不是让它从工程记忆里推断。
- **每条产出带 `type`**，取值 `工具 / 游戏 / 趣味 / 外观 / 多媒体 / 传播`。prompt 明确要求**至少覆盖 3 种**，并且要主动去找游戏、趣味、外观、多媒体、传播方向。

模型如果还是交回一份全是「工具」的清单，host 会**用更强硬的措辞重试一次**；重试仍是同一个类型就**保留内容**，只在界面上标出「今天所有条目都是同一个类型」——**宁可告诉你它没变宽，也不假装这是一份均衡的日报。**

## 独立实现，不是 fork

这是这个插件的硬规则，也是它和"fork 别人的仓改一改"的根本区别：

- 禁止 `gh repo fork`；禁止 clone 原仓库后在它基础上改；禁止整段搬运原版代码。
- 建的是**你自己的**仓库（`gh repo create <你的项目名>`），不是从原仓库派生。
- README 里必须写明灵感来自哪个原仓库（带 URL），并说清你做了什么不同。
- 确实需要复用原版代码片段时，先确认它的 LICENSE 允许，并在文件里保留原版权声明。

**借鉴思路可以，复制代码不行。** 所以校验里还有一条：如果模型把 `title` 写成原仓库的名字（`dsh-alpha`、`DSH Alpha`、`acme/dsh-alpha` 都算），这条会被当作"改名重发"丢弃并计数。

两个 `title` 都必须**小写 ASCII、形如 `dsh-xxx`**——它会被直接用作 GitHub 仓库名和本地目录名。

## 四条硬保证

模型的输出在落到你眼前之前，要过四道纯函数校验（`src/report.js`，全部有单测）：

1. **不许编造来源。** 每条改进的 `basedOn` 必须**逐字**命中预筛池；不命中就丢弃并计数。链接和分类也取自语料，不采信模型给的 URL。
2. **不许说空话。** `delta` 为空、或只是「做得更好 / 增强体验 / 优化性能」这类空话，丢弃并计数。`why` 同理（「很强大 / 值得一试」会被丢弃）。
3. **不许改名重发。** `title` 撞上原仓库的名字就丢弃并计数，见上一节。两栏之间也不许重名——名字一样的两条你分不出来，按名字批准也会歧义。名字里连字母数字都没有（`!!!` 这种）单独计为「无名字」，因为它没法当仓库名。
4. **证据要么可核验，要么标明是猜的。** `evidence` 必须引用池子里的某个 repo 或一个真实链接；拿不出来就只能写 `无直接证据`，界面上会打上「未经证实」的标记，不会冒充调研结论。

界面上会显示每次生成丢弃了多少条、分别因为什么被丢，所以模型糊弄不了你。

## 装

```sh
# npm 版 CLI 管理的 profile
dsh plugin --profile <name> add <插件目录>

# 桌面版：desktop profile 由 Electron app 独占，npm 版 CLI 会被拒绝——
#   error: profile "desktop" is managed exclusively by the Electron application
# 用它自带的那个 CLI 才行（在 app 的 resources/runtime/cli/bin/dsh 下）：
"<app>/resources/runtime/cli/bin/dsh" plugin --profile desktop add <插件目录>
```

装完重启一次，对话视图里会出现「日报」Tab。

> **改 host 半区必须重启 app。** Node 按 URL 缓存 ES 模块，`plugin_manager` 的关开、
> 甚至卸载 bundle 再装回，都不会换掉已经加载的 host 代码。客户端半区可以热更新，host 不行。

## 用

- **立即生成** —— 不用等 11:00，随时手动跑一次。
- **改进项的「做这个」** —— 批准一条改进，把它投给当前会话。
- **灵感的「做这个」** —— 批准一个新方向，投递的是另一套框架（说明这是生态里还没有的东西）。
- **「不感兴趣」** —— 把这条的来源记进 seen，以后不再出现。

点下去之后，插件**不自己开发**。它把一条消息投递给当前活跃的会话（`ctx.agents.roots()` + `agent.runMaintenance()` + `agent.followup()`，和官方 `dsh-schedule` 投递提醒用的是同一条通路），agent 拿自己的常规工具去干活。

投递的消息里写死了交付契约：

1. **独立实现，不要 fork。** 禁止 `gh repo fork`；禁止 clone 原仓库改；禁止整段搬运原版代码
2. 在 `D:\Projects\<你自己的项目名>` 起工程，骨架照抄 `dsh-warden`
3. 写实现和测试，`node --test` 必须全绿，测试不过不许发布
4. 推送前跑三步检查：密钥扫描、`.gitignore` 核对、无关文件清理
5. **三步检查任一命中就停下来报告，不许推送**
6. 全过才用 `gh repo create <你自己的项目名> --public --source . --push` 建**你自己的**仓库
7. 回报仓库 URL、测试通过数、commit hash、三步检查结果，以及**你和原版的具体差异**

**没有活跃会话时，批准不会丢。** 它进 pending 队列，并在 `agent/created` 时自动重试——和官方提醒"等会话回来再投递"的行为一致。

## 配置

`apply(ctx, config)` 的 config 全部可覆盖：

| key | 默认 | 说明 |
| --- | --- | --- |
| `hour` / `minute` | `11` / `0` | 每日触发时刻（本地时间） |
| `maxCandidates` | `60` | 送进模型的预筛池上限 |
| `perCategory` | `4` | 每个分类最多进池几个。语料有 23 个分类，所以 4 足够填满 60；设成 2 只能凑到 46 |
| `maxImprovements` | `10` | 日报最多几条改进项 |
| `maxIdeas` | `3` | 日报最多几条灵感 |
| `maxTokens` | `16000` | 单次生成的最大输出 token。要留出推理余量：**推理 token 也算在里面**，所以给 JSON 的余量比这个数字小得多 |
| `historyKeep` | `30` | 保留多少天历史 |
| `profileName` | `desktop` | 读哪个 profile 的已装插件清单 |
| `corpusPath` | `$DSH_HOME/daily/corpus.csv` | 语料。不存在时从 `seedCorpus` 复制一份 |
| `seedCorpus` | 无 | 首次播种来源；不配就是空语料 |
| `projectsRoot` | `~/Projects` | 交给 agent 的契约里，新工程建在哪 |
| `templateRoot` | 无 | 骨架照抄哪个现成插件；不配时契约改为描述骨架要求 |

### 本机配置：`$DSH_HOME/daily/config.json`

上面凡是跟**你这台机器**有关的 key（语料在哪、项目建在哪、照抄哪个骨架），都不写进仓库。公开仓库里塞死某台机器的绝对路径，既泄露本机布局，也让别人 clone 下来开箱即废。

本机值放在 `$DSH_HOME/daily/config.json`，插件加载时读：

```json
{
  "seedCorpus": "D:\\somewhere\\plugins.csv",
  "projectsRoot": "D:\\Projects",
  "templateRoot": "D:\\Projects\\some-skeleton"
}
```

优先级：**显式 config > `config.json` > 内置通用默认**。文件坏了（JSON 不合法）只退回默认值，不会让插件加载失败。

## 数据落在哪

| 路径 | 内容 |
| --- | --- |
| `$DSH_HOME/daily/corpus.csv` | 插件语料，插件自己持有一份 |
| `$DSH_HOME/daily/reports/YYYY-MM-DD.json` | 每天的完整日报（含每条的类型、丢弃统计与原始回复） |
| `$DSH_HOME/daily/state.json` | seen（来源仓库）、提过的灵感标题、历史索引、批准记录 |
| `$DSH_HOME/daily/approvals.jsonl` | 批准审计流水 |

HTTP 面（挂在 `webServer` 的 `/dsh-daily` 前缀下）：

```
GET  /dsh-daily/state              配置、状态、当天日报、历史、批准记录
POST /dsh-daily/run                立即生成（202，异步）
POST /dsh-daily/approve            { title } 按项目名批准（改进项或灵感都行），或 { basedOn } 按来源批准
POST /dsh-daily/skip               { repo } 不再出现
```

## 容错姿态

这个插件任何一处坏掉都不该拖垮 harness，所以：读不到语料、模型路由不可用、模型返回的不是 JSON、stream 以 `finish{kind:'error'}` 结束、agent 正忙——全部降级成界面上的一行状态，不抛异常。`webServer.register` 失败也只是没有 HTTP 面，host 半区和定时器照常工作。缺的画像来源会显式列在 `status`/报告里，而不是悄悄生成一份泛泛的日报。

**模型偶尔吐不出 JSON 是常态，不是异常。** 本机实测 `deepseek-flash` 在这条链路上会返回无法解析的回复（同一个模型给另一个插件做审查时 13 次里有 2 次失败）。所以生成不是一锤子买卖：

1. 第一次不解析 → 追加「只输出 JSON 本身」的更强约束**重试一次**；
2. 重试仍不解析 → 把 `finish` 原因、收到的字符数和**原始回复前 2000 字**写进报告，同时在界面上报错。

这一条是刻意的：**空报告绝不能被伪装成「今天没有好东西」。** 没有这段，模型失败和风平浪静在界面上长得一模一样。

### 被截断的回复：救回来，而不是扔掉

`finish=max-tokens` 意味着**输出预算用尽**——注意**推理 token 也计入 `maxTokens`**，所以给 JSON 的余量比看上去少得多。每个 `delta` 变成一句具体的话之后，一份日报的体积大约翻了一倍，8000 的预算就不够了（默认已提到 16000）。

但这暴露了一个更糟的设计错误：**被截断的回复当时是被整份丢掉的。** 一份在最后一条写到一半的回复里，前面几条往往是**完整的、合格的**——把它们扔掉等于丢掉了模型已经做出来的工作，界面上还会显示「0 条」配一个错误，是两头都最坏的结果。

现在的处理：

1. **先补救再放弃。** 字符串感知的括号扫描器把每个**完整闭合**的对象捞出来（`salvageReport`）。只有完整的才要，而且它们走**和其他条目完全一样的校验**——补救可以增加条目，但绝不能让不合格的混进来。
2. **按预算重试。** 重试时不再重复同样的要求（那样只会再次超预算），而是明确要求**更短的清单**：最多 4 个改进项、2 个灵感，每条 60 字以内。**写不完整不如少写几条。**
3. **两版取内容多的那版。** 一份「完整但空」的重试**不能**顶掉一份有 3 条真内容的补救结果——告诉用户「今天没有值得做的」比告诉他「还有更多没写完」更糟。
4. **如实标注。** 救回来的报告带 `truncated: true`，界面上是**琥珀色提示**（不是红色错误）：写完的 N 条已保留，其余丢失。它既不是失败，也不是完整报告。

对着真实失败数据验过：那份 3498 字符、`parseReportJson` 全盘失败的回复，补救逻辑捞回了 **3 条完整改进项**，全部通过校验、零丢弃，覆盖工具/多媒体/外观三类。

## 开发

```sh
node --test          # 143 个测试
node scripts/build.mjs
```

零依赖构建：host 半区只 import `node:` 内置模块和同目录兄弟模块，所以复制 `src/*.js` 到 `lib/` 就是完整构建——没有会在安装时挂掉的 devDependency。client 半区是 CJS，构建时把唯一的相对 require（样式表）内联进去，然后用 `new Function()` 编译一次，并在浏览器之外直接 import `lib/index.js` 校验导出，坏构建在构建期就炸。

测试用桩 Context 驱动真实的 `apply()`（`test/host.test.mjs`），跑的是真的排期、真的池子过滤、真的输出校验、真的持久化和真的投递，不是这些逻辑的复刻。`test/corpus.test.mjs` 里有一条直接跑真实 3727 条语料的用例。`test/client.test.mjs` 把客户端半区也拉进测试（只桩掉 React），管住 Tab 的注册契约和版本错配的判断方向。
